# 💰 FinancePlanner

**Личный финансовый планировщик с математическим ядром.**
Не «предсказатель будущего», а **калькулятор последствий твоих решений**: видит кассовые разрывы за месяцы до того, как они случатся, и честно отвечает на вопрос «а что, если…?».

## 🎯 Зачем это нужно

Большинство бюджетных приложений отвечают на вопрос **«куда ушли деньги?»** — то есть смотрят в прошлое.
FinancePlanner смотрит **вперёд** и отвечает на три вопроса, которые реально влияют на жизнь:

1. **Дотяну ли я до выплаты?** — спринты и точки дефицита.
2. **Что будет, если я потрачу / перенесу / заработаю X?** — what-if анализ и календарь с drag&drop.
3. **Когда я стану свободен и сколько накоплю?** — долгосрочный прогноз и ежемесячный излишек.

Приложение родилось из реальной ситуации: зарплата двумя выплатами, кредит под 30%, свадьба, рыбалка, пересылка за границу и вечное «хватит ли до 20-го числа». Вместо того чтобы держать это в голове и табличках, вся картина собрана в одну модель.

## 🧠 Суть приложения: три ключевые идеи

### 1. Спринты вместо месяцев

Бюджет человека с выплатами 1-го и 15-го живёт **не по календарным месяцам, а по периодам между выплатами**. Поэтому базовая единица планирования — **спринт**: от выплаты до выплаты.

Для каждого спринта модель считает: доходы окна, постоянные расходы, переменные (дневная норма × число дней), события — и выдаёт **доступный бюджет** со статусом `ok / tight / deficit`.

### 2. Необходимый резерв — математическая гарантия, а не оценка

Пунктирная линия на графике — это **минимум, который должен быть на руках в каждую дату**, чтобы все будущие обязательства были покрыты:

```
required[i] = max( 0,  max_{j≥i}  Σ_{k=i..j} (расходы[k] − доходы[k]) )
```

Из формулы следует строгое свойство, которое проверено юнит-тестом:

> **Если линия баланса выше пунктира — дефицит на горизонте невозможен.**
> Если баланс опустился ниже — дефицит гарантирован, и модель показывает его дату и глубину.

Это не «прогноз с погрешностью», это теорема о твоих собственных вводных.

### 3. Модель = калькулятор плана, точность = точность вводных

Приложение не угадывает будущее — оно **точно просчитывает введённый план**. Поэтому:

| Горизонт | Чему верить | Погрешность |
|----------|-------------|-------------|
| 1–2 недели | и сумме, и датам | ±300–800 ₽ |
| 1–3 месяца | **факту и дате** кассового разрыва | ±1–2 тыс. ₽ |
| 6 месяцев | тренду и ежемесячному излишку | абсолюту не верь |

Правило эксплуатации: **каждые 1-е и 15-е** обнови «текущий баланс» и отметь выполненные события — прогноз перепривяжется к реальности (скользящее планирование).

## 🧱 Архитектура

```
┌────────────────────────────  Web (Flask + JS)  ────────────────────────────┐
│  Дашборд · Прогноз · Спринты · Календарь · События · Что-если · Настройки  │
└──────────────────────────────────┬─────────────────────────────────────────┘
                                   │  REST API (JSON)
┌──────────────────────────────────▼─────────────────────────────────────────┐
│                        MathCore — чистая математика                        │
│  engine.py — фасад                                                         │
│  ┌─────────────┐ ┌───────────┐ ┌─────────────┐ ┌──────────┐ ┌───────────┐  │
│  │ forecast.py │ │ sprint.py │ │ deviation.py│ │ config.py│ │ models.py │  │
│  │ баланс по   │ │ периоды   │ │ дефициты,   │ │ JSON I/O │ │ данные +  │  │
│  │ дням        │ │ между     │ │ резерв,     │ │ + бэкапы │ │ серии     │  │
│  │             │ │ выплатами │ │ runway,     │ │          │ │ событий   │  │
│  │             │ │           │ │ what-if     │ │          │ │           │  │
│  └─────────────┘ └───────────┘ └─────────────┘ └──────────┘ └───────────┘  │
└────────────────────────────────────────────────────────────────────────────┘
```

**Главный принцип: в MathCore нет ни одного хардкода.** Доходы, расходы, дни выплат, события и серии — всё вводится пользователем или загружается из `config.json`. Ядро не знает про «зарплату» и «кредит» — оно знает про потоки денег с датами.

MathCore **полностью независим от веба**: его можно подключить к Telegram-боту, CLI или другому фреймворку — Flask лишь отдаёт JSON.

```python
from mathcore import MathCore

core = MathCore.from_config_file('config.json')

core.get_forecast(days=90)      # баланс по дням + необходимый резерв + дефициты
core.get_sprints(count=6)       # спринты: доступный бюджет каждого периода
core.get_risks()                # дефициты, напряжённые периоды, runway
core.get_summary()              # сводка месяца: доход/расход/излишек
core.what_if(extra_income=5000) # «что если» без изменения конфига
```

## ✨ Возможности

### 📊 Дашборд
Сводка месяца, структура расходов (донат), «доходы vs расходы», риски и дефициты.

### 📈 Прогноз баланса (30–365 дней)
- линия баланса по дням со ступеньками в дни выплат;
- **пунктир необходимого резерва** — ранний сигнал будущих дыр;
- зебра-подсветка спринтов и маркеры выплат/событий;
- список точек дефицита: дата, глубина, дней до восстановления.

### 🏃 Спринты
Текущий спринт считается честно: «на руках + будущие доходы − будущие расходы», постоянные текущего цикла считаются оплаченными. Любой будущий период — одним взглядом: `+2 100 ₽`, `tight`, `deficit`.

### 📅 Календарь (как в Google Calendar)
- виды **месяц / неделя / день**;
- клик по дню — создание события, клик по событию — редактирование;
- **drag&drop** — перенос траты на другую дату с мгновенным пересчётом прогноза;
- 💵 выплаты и 💳 постоянные расходы отображаются автоматически;
- **повторяющиеся события** («повторять ежемесячно до …») — закупы, подписки, регулярные платежи раскладываются по месяцам автоматически.

### 🔮 Что-если
«Дополнительный доход / расход / отмена событий» → влияние на баланс и дефициты **до** того, как ты реально потратил деньги.

### ⚙️ Данные
- всё редактируется из интерфейса или импортом/экспортом JSON;
- автосохранение в `config.json` + **бэкап предыдущей версии** при каждом сохранении;
- дни выплат, состав доходов и расходов — полностью твои.

## 📐 Соглашения модели (читать обязательно)

1. **«Текущий баланс» = деньги на руках СЕЙЧАС, включая сегодняшнюю выплату.** Поэтому в день старта прогнода доходы не прибавляются повторно.
2. **Постоянные расходы первого цикла не списываются** — они оплачены с открывающей выплаты и уже сидят в балансе. Со второго цикла списываются в свой день.
3. **Переменные расходы** размазаны равномерно по дням (месячная сумма ÷ 30).
4. **События** списываются в свою дату; серии `monthly` раскрываются до `repeat_end` или конца горизонта.

Эти соглашения отражают реальное поведение человека с зарплатным циклом, а не абстрактную бухгалтерию — в этом источник точности модели на коротких горизонтах.

## 🧪 Тесты

```bash
python -m pytest tests -v        # 14 тестов
python report.py                 # отчёт «что почём» по сценарию до января 2027
```

Что покрыто:
- раскрытие месячных серий и клампование дат (`31.01 + 1 мес → 28.02`);
- соглашения прогноза (день старта, первый цикл, зарплаты);
- **свойство-гарантия необходимого резерва** (баланс ≥ резерва ⇒ дефицит невозможен);
- честность текущего спринта;
- сквозной сценарий «реальный план до января 2027»: единственная дыра в конце августа, глубина ограничена, концов месяцев и ежемесячный излишек ≈ +18 340 ₽ сходятся с ручным расчётом.

## ⚠️ Дисклеймер

FinancePlanner — инструмент принятия решений, а не финансовая рекомендация.
Модель настолько же честна, насколько свежи введённые в неё данные: обновляй баланс в дни выплат — и она будет видеть твоё будущее на месяцы вперёд.
